### 2.1 Основы backend и HTTP

#### Теория — занятие 1 (до написания кода)

**Протокол HTTP** — текстовый протокол запрос/ответ поверх TCP. Клиент отправляет запрос, сервер возвращает ответ. Соединение без сохранения состояния (stateless).

**Структура HTTP-сессии:**
```
# Запрос
POST /tasks HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer <token>

{"title": "Buy milk"}

# Ответ
HTTP/1.1 201 Created
Content-Type: application/json
Location: /tasks/42

{"id": 42, "title": "Buy milk"}
```

**Заголовки (headers)** — метаданные запроса/ответа в формате `Имя: Значение`:
- `Content-Type` — формат тела (`application/json`, `text/html`, `multipart/form-data`)
- `Authorization` — токен доступа
- `Accept` — какой формат ответа принимает клиент
- `Cache-Control` — директивы кэширования
- `Set-Cookie` / `Cookie` — управление сессией
- `CORS-заголовки` — `Access-Control-Allow-Origin` и др.

**URL и его части:**
```
https://api.example.com:443/tasks/42?sort=asc&page=1#section
  │      │               │   │         │              │
scheme  host            port path      query        fragment
```
- `path` — иерархический идентификатор ресурса
- `query string` — параметры фильтрации/пагинации; символы `пробел`, `&`, `=`, кириллица — **обязательно кодируются** через percent-encoding (`%20`, `%26`)
- `fragment` — обрабатывается браузером, на сервер не доходит

**Percent-encoding vs Base64:**
- **Percent-encoding** (`%XX`) — нужен в URL; заменяет символы, недопустимые или зарезервированные в URL
- **Base64** — нужен когда двоичные или произвольные данные нужно передать через текстовый канал, который не поддерживает произвольные байты:
  - `Authorization: Basic dXNlcjpwYXNz` (user:pass в base64)
  - данные изображений/файлов внутри JSON (`"avatar": "data:image/png;base64,..."`)
  - JWT-токен состоит из трёх base64url-кодированных частей (header.payload.signature)

> Важно: base64 — это **кодирование**, не шифрование. Данные легко декодировать.

**Версии протокола:**
- HTTP/1.1 — одно соединение, pipeline (редко), keep-alive
- HTTP/2 — мультиплексирование потоков, сжатие заголовков (HPACK)
- HTTP/3 — поверх QUIC/UDP, устойчивость к packet loss

#### Практикум: ручной HTTP (Node.js, строка за строкой)

1. Создай `server.js` (минимальный сервер на встроенном `http`):

```js
const http = require("http");

const server = http.createServer((req, res) => {
  let body = "";
  req.on("data", (chunk) => (body += chunk));
  req.on("end", () => {
    console.log("---- REQUEST ----");
    console.log(req.method, req.url, "HTTP/" + req.httpVersion);
    console.log(req.headers);
    console.log("body:", body || "<empty>");
    console.log("-----------------");

    res.statusCode = 200;
    res.setHeader("Content-Type", "application/json");
    res.end(JSON.stringify({ ok: true, method: req.method, url: req.url }));
  });
});

server.listen(8080, () => {
  console.log("Server: http://127.0.0.1:8080");
});
```

2. Запусти сервер:

```bash
node server.js
```

3. Создай `manual-http-client.js` (TCP-клиент для ручного ввода HTTP):

```js
const net = require("net");
const readline = require("readline");

const socket = net.createConnection({ host: "127.0.0.1", port: 8080 }, () => {
  console.log("Connected to 127.0.0.1:8080");
  console.log("Type HTTP lines manually");
  console.log("/end -> send empty line");
  console.log("/quit -> close client");
});

socket.on("data", (data) => process.stdout.write(data.toString()));
socket.on("end", () => console.log("\nConnection closed by server"));
socket.on("error", (err) => console.error("Socket error:", err.message));

const rl = readline.createInterface({
  input: process.stdin,
  output: process.stdout,
  terminal: true,
});

rl.on("line", (line) => {
  if (line === "/quit") {
    socket.end();
    rl.close();
    return;
  }
  if (line === "/end") {
    socket.write("\r\n");
    return;
  }
  socket.write(line + "\r\n");
});
```

4. Запусти клиент во втором терминале:

```bash
node manual-http-client.js
```

5. Введи `GET` руками (каждая строка + Enter):

```http
GET /hello HTTP/1.1
Host: 127.0.0.1:8080
Connection: close
/end
```

6. Введи `POST` руками (проверь `Content-Length`):

```http
POST /tasks HTTP/1.1
Host: 127.0.0.1:8080
Content-Type: application/json
Content-Length: 13
Connection: close
/end
{"x":"test"}
```

7. Сравни, что отправил клиент, с тем, что сервер вывел в `req.headers` и `body`.

## 4. Ответы на вопросы

### A1 HTTP-статусы

| Код | Когда использовать |
|-----|--------------------|
| 200 | Успешный запрос (GET, PUT, PATCH вернули данные) |
| 201 | Ресурс создан (POST) |
| 204 | Успех, тело пустое (DELETE, PATCH без возврата) |
| 400 | Некорректные данные от клиента (нарушение схемы) |
| 401 | Нет токена или токен недействителен |
| 403 | Токен есть, но прав недостаточно |
| 404 | Ресурс не найден |
| 409 | Конфликт (email уже зарегистрирован) |
| 422 | Запрос синтаксически верен, но семантически не обработан |
| 429 | Слишком много запросов (rate limit) |
| 500 | Непредвиденная ошибка на сервере |

### A2 Edge-cases и зачем они важны

Edge-case — граничное значение или нестандартный сценарий: пустой массив, `null`, ноль, максимально длинная строка, отрицательное число.  
Именно в граничных случаях прячется большинство реальных багов — основной поток тесты покрывают легко, а обрыв на границе ломает продакшн.  
Правило: для каждой функции определи минимум: пустой ввод, максимальный ввод, невалидный тип.

### A3 Индексы

Индекс — дополнительная структура (B-tree по умолчанию в PostgreSQL), позволяющая искать строки без сканирования всей таблицы.  

**Когда полезен:** поле часто используется в `WHERE`, `JOIN ON`, `ORDER BY`, `GROUP BY`.  
**Когда вреден:**  
- колонка с малой селективностью (булевый флаг) — планировщик всё равно выберет seq scan;  
- таблица очень маленькая;  
- много записей (`INSERT`/`UPDATE`/`DELETE`) — каждая запись требует обновления индекса.  

Проверяй план: `EXPLAIN ANALYZE SELECT ...` — смотри на `Seq Scan` vs `Index Scan` и на `actual time`.

### A4 ACID

| Свойство | Смысл |
|----------|-------|
| **Atomicity** (атомарность) | Транзакция выполняется целиком или откатывается полностью |
| **Consistency** (согласованность) | После транзакции БД остаётся в допустимом состоянии (все constraints выполнены) |
| **Isolation** (изоляция) | Параллельные транзакции не видят промежуточных состояний друг друга (по умолчанию в PG — Read Committed) |
| **Durability** (долговечность) | После фиксации (COMMIT) данные сохраняются даже при сбое |

Уровни изоляции по возрастанию строгости: Read Uncommitted → Read Committed → Repeatable Read → Serializable.

### A5 Стратегии кэша

**Cache-aside (ленивая загрузка):** приложение сначала смотрит в кэш, при промахе — идёт в БД и сохраняет результат. Самый распространённый паттерн.  
**Write-through:** запись идёт одновременно в кэш и БД — данные всегда актуальны, но запись медленнее.  
**Write-behind (write-back):** запись идёт только в кэш, а в БД — асинхронно. Высокая скорость записи, риск потери данных.

**Риски невалидного кэша:**  
- пользователь видит устаревшие данные (stale data);  
- после изменения записи в БД нужно явно инвалидировать ключ (`DEL key`) или использовать короткий TTL.

**Redis помимо кэша:** сессии пользователей, pub/sub, очереди задач (Bull/BullMQ), rate limiting, лидерборды (sorted sets), распределённые блокировки.

### A6 Монолит vs микросервисы

**Монолит** — единое приложение. Проще разрабатывать, дебажить, деплоить. Для junior-проектов и стартапов — правильный выбор по умолчанию.  

**Микросервисы** — набор независимых сервисов. Полезны, когда:  
- разные части системы масштабируются по-разному;  
- разные команды работают независимо;  
- нужны разные стеки для отдельных компонентов.

**Цена микросервисов:** сетевые вызовы вместо функций, distributed tracing, сложность operational.  
Для junior-интервью достаточно знать разницу и уметь объяснить, почему монолит — это не плохо.

### A7 Базовая безопасность

**SQL injection:** параметризованные запросы / prepared statements. ORM защищают автоматически при правильном использовании. Никогда не конкатенируй пользовательский ввод в строку запроса.

**XSS (Cross-Site Scripting):** актуально для frontend. На backend — санитизируй вывод HTML, устанавливай `Content-Security-Policy` через `helmet`.

**CSRF:** используй `SameSite=Strict/Lax` cookies, CSRF-токены (для cookie-based сессий). JWT в `Authorization` заголовке менее подвержен CSRF.

**Хранение паролей:** всегда хешируй с солью — `bcrypt` (cost ≥ 12) или `argon2id`. Никогда: MD5, SHA1, plain text, симметричное шифрование (reversible).

**Другие пункты OWASP Top 10:** Broken Access Control, Security Misconfiguration, Vulnerable Components — на практике покрываются: проверкой прав в middleware, актуальными зависимостями, минимальными правами для сервисных аккаунтов.

### A8 Покрытие тестами

100% coverage означает только, что каждая строка была выполнена хотя бы раз. Это не гарантирует:  
- проверку всех комбинаций условий (branch coverage);  
- корректность логики (можно выполнить строку, не проверив возвращаемое значение);  
- покрытие интеграции компонентов.

**Практическое правило:** цель — покрыть критичную бизнес-логику, граничные случаи и пути ошибок, а не гнаться за числом.

**Пирамида тестов:** много быстрых unit → меньше медленных интеграционных → минимум e2e.

### A9 Secrets и env

Что **нельзя** коммитить: пароли БД, API-ключи, JWT-секреты, приватные ключи TLS.  

**Как хранить:**  
- локально — файл `.env` (добавлен в `.gitignore`);  
- CI/CD — secrets в GitHub Actions / GitLab CI (masked variables);  
- продакшн — переменные окружения платформы (Railway, Fly.io) или менеджер секретов (Vault, AWS Secrets Manager).

Если секрет случайно попал в git — **сразу** ротируй его (смени пароль/ключ), история остаётся навсегда даже после `git rm`.

### A10 Диагностика latency

1. **Логи с таймингами** — добавь замер времени ответа на уровне middleware, смотри на статистику по endpoint-ам.  
2. **EXPLAIN ANALYZE** — медленные SQL-запросы чаще всего первая причина; ищи Seq Scan на больших таблицах.  
3. **N+1 проблема** — ORM по умолчанию делает запрос на каждую строку; решение — eager loading (`include` в Prisma, `relations` в TypeORM).  
4. **Нет кэша** — повторяющиеся тяжёлые запросы без кэширования.  
5. **Внешние сервисы** — тайм-аут или медленный ответ стороннего API; добавь тайм-аут и отдельный таймер.  
6. **Утечка памяти / GC pause** — смотри на CPU/Memory графики; в Node.js — `--inspect` + heap snapshot.

Порядок действий: измерь → локализуй → исправь → измерь снова.

## 6. Ответы на вопросы

### A1 HTTP-статусы
- `200 OK`: успешный запрос с телом ответа.
- `201 Created`: создан новый ресурс.
- `204 No Content`: успех без тела ответа.
- `400 Bad Request`: некорректный запрос.
- `404 Not Found`: ресурс не найден.
- `409 Conflict`: конфликт состояния (например, дубликат).
- `422 Unprocessable Entity`: валидация не прошла.
- `500 Internal Server Error`: ошибка сервера.

### A2 Edge-cases
- Edge-cases выявляют баги на границах входных данных: пустые значения, `null`, длинные строки, переполнение, дубликаты.
- Без edge-case тестов система кажется рабочей, но падает в проде на редких сценариях.

### A3 Индексы
- Индекс ускоряет чтение и поиск, но замедляет запись и занимает место.
- Индекс полезен на колонках фильтрации, сортировки, JOIN.
- Избыточные индексы ухудшают производительность INSERT/UPDATE/DELETE.

### A4 ACID
- Atomicity: транзакция выполняется целиком или откатывается.
- Consistency: БД переходит из одного корректного состояния в другое.
- Isolation: параллельные транзакции не ломают друг друга.
- Durability: подтвержденные изменения не теряются.

### A5 Стратегии кэша
- Cache aside: приложение само читает/пишет кэш.
- Write-through: запись сразу в кэш и БД.
- TTL и инвалидация обязательны, иначе старые данные приводят к ошибкам.

### A6 Монолит vs микросервисы
- Монолит проще на старте: меньше операционной сложности.
- Микросервисы дают изоляцию и масштабирование, но повышают сложность инфраструктуры.
- Для Junior и первых проектов обычно достаточно модульного монолита.

### A7 Базовая безопасность
- SQL injection: параметризованные запросы/ORM.
- XSS: экранирование и CSP, осторожность с пользовательским HTML.
- CSRF: токены и SameSite-cookie.
- Пароли: только salted hash (bcrypt/argon2), никогда не хранить plaintext.

### A8 Покрытие тестами
- Высокое покрытие не проверяет качество самих проверок.
- Можно иметь 100% coverage и не тестировать важные бизнес-сценарии.
- Нужны осмысленные тест-кейсы, включая негативные и интеграционные.

### A9 Secrets и env
- Никогда не коммитить API ключи, пароли, private keys.
- Использовать `.env` локально и секрет-хранилища в CI/CD и облаке.
- Добавить пример `.env.example` без секретов.

### A10 Диагностика latency
- Проверить: БД-запросы, индексы, сетевые вызовы, блокирующие операции.
- Сравнить p50/p95/p99 latency.
- Добавить трассировку запроса по слоям (API -> service -> DB/external).

- Важна структура: проблема -> варианты -> компромисс -> выбор.
- Не угадывать уверенно, лучше показать инженерное мышление.
