### 2.1 Основы backend и HTTP

#### Теория — занятие 1 (до написания кода)

**Протокол HTTP** — текстовый протокол запрос/ответ поверх TCP. Клиент отправляет запрос, сервер возвращает ответ. Соединение без сохранения состояния (stateless).

**Структура HTTP-сессии:**
```
# Запрос
POST /tasks HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer <token>

{"title": "Buy milk"}

# Ответ
HTTP/1.1 201 Created
Content-Type: application/json
Location: /tasks/42

{"id": 42, "title": "Buy milk"}
```

**Заголовки (headers)** — метаданные запроса/ответа в формате `Имя: Значение`:
- `Content-Type` — формат тела (`application/json`, `text/html`, `multipart/form-data`)
- `Authorization` — токен доступа
- `Accept` — какой формат ответа принимает клиент
- `Cache-Control` — директивы кэширования
- `Set-Cookie` / `Cookie` — управление сессией
- `CORS-заголовки` — `Access-Control-Allow-Origin` и др.

**Cookies** — механизм хранения небольших данных на клиенте; браузер автоматически отправляет их с каждым запросом к домену.

Формат заголовка `Set-Cookie`:
```
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
```

| Атрибут | Назначение |
|---------|----------|
| `HttpOnly` | JS не может читать куку — защита от XSS-кражи токена |
| `Secure` | Кука передаётся только по HTTPS |
| `SameSite=Strict` | Кука не отправляется с других доменов — полная защита от CSRF |
| `SameSite=Lax` | Кука отправляется при навигации (GET), но не при кросс-сайтовых POST/AJAX |
| `SameSite=None` | Кука отправляется всегда (требует `Secure`) — для сторонних сервисов |
| `Expires` / `Max-Age` | Срок жизни. **Без них — сессионная кука** (удаляется при закрытии браузера) |
| `Domain`, `Path` | Область действия куки |

**Типы cookies:**
- **Session cookie** — без `Expires`/`Max-Age`, живёт до закрытия браузера.
- **Persistent cookie** — хранится на диске, задан срок. Используется для «Запомни меня».
- **HttpOnly cookie** — закрыта от JS, безопасно хранить session token или JWT.
- **Third-party cookie** — установлена чужим доменом (аналитика, реклама). Блокируется по умолчанию в Safari/Firefox.

**Cookies vs Web Storage:**

| | Cookie | localStorage | sessionStorage |
|--|--------|-------------|----------------|
| Отправляется с запросами | Автоматически | Нет | Нет |
| Доступ из JS | Только без `HttpOnly` | Да | Да |
| Срок жизни | Настраиваемый | Вечно (до очистки) | Вкладка |
| Размер | ~4 КБ | ~5–10 МБ | ~5–10 МБ |
| Уязвимость к XSS | `HttpOnly` защищает | Уязвим | Уязвим |

**URL и его части:**
```
https://api.example.com:443/tasks/42?sort=asc&page=1#section
  │      │               │   │         │              │
scheme  host            port path      query        fragment
```
- `path` — иерархический идентификатор ресурса
- `query string` — параметры фильтрации/пагинации; символы `пробел`, `&`, `=`, кириллица — **обязательно кодируются** через percent-encoding (`%20`, `%26`)
- `fragment` — обрабатывается браузером, на сервер не доходит

**Percent-encoding vs Base64:**
- **Percent-encoding** (`%XX`) — нужен в URL; заменяет символы, недопустимые или зарезервированные в URL
- **Base64** — нужен когда двоичные или произвольные данные нужно передать через текстовый канал, который не поддерживает произвольные байты:
  - `Authorization: Basic dXNlcjpwYXNz` (user:pass в base64)
  - данные изображений/файлов внутри JSON (`"avatar": "data:image/png;base64,..."`)
  - JWT-токен состоит из трёх base64url-кодированных частей (header.payload.signature)

> Важно: base64 — это **кодирование**, не шифрование. Данные легко декодировать.

**Версии протокола:**
- HTTP/1.1 — одно соединение, pipeline (редко), keep-alive
- HTTP/2 — мультиплексирование потоков, сжатие заголовков (HPACK)
- HTTP/3 — поверх QUIC/UDP, устойчивость к packet loss

**Статический контент в Express:**

`express.static` — встроенный middleware для раздачи файлов с диска (HTML, CSS, JS, изображений) без написания маршрутов вручную.

```js
const express = require("express");
const path = require("path");
const app = express();

// Файлы из папки public/ доступны по корневому URL
app.use(express.static(path.join(__dirname, "public")));
// public/index.html → GET /
// public/style.css  → GET /style.css

// С базовым путём
app.use("/static", express.static(path.join(__dirname, "public")));
// public/style.css → GET /static/style.css
```

Как обрабатывается запрос: Express ищет файл на диске → если найден, определяет MIME-тип (`text/css`, `image/png` и т.д.), выставляет заголовки кэша и отдаёт файл → если не найден, вызывает `next()` и запрос идёт к следующему middleware/роуту.

**Заголовки кэширования для статики:**

| Заголовок | Поведение |
|-----------|----------|
| `ETag: "abc123"` | Fingerprint содержимого. Браузер шлёт `If-None-Match`; если файл не изменился — сервер отвечает `304 Not Modified` (тело не передаётся) |
| `Last-Modified: <date>` | Дата изменения файла. Браузер шлёт `If-Modified-Since`; не изменился → `304` |
| `Cache-Control: max-age=N` | Браузер кэширует N секунд **без обращения к серверу** |

По умолчанию `express.static` выставляет `ETag` и `Last-Modified`. `max-age` можно задать через опцию `{ maxAge: '1d' }`.

> Разница: `ETag`/`304` — браузер всё равно идёт к серверу, но тело не передаётся. `Cache-Control: max-age` — браузер вообще не делает запрос до истечения срока.

#### Практикум: ручной HTTP (Node.js, строка за строкой)

1. Создай `server.js` (минимальный сервер на встроенном `http`):

```js
const http = require("http");

const server = http.createServer((req, res) => {
  let body = "";
  req.on("data", (chunk) => (body += chunk));
  req.on("end", () => {
    console.log("---- REQUEST ----");
    console.log(req.method, req.url, "HTTP/" + req.httpVersion);
    console.log(req.headers);
    console.log("body:", body || "<empty>");
    console.log("-----------------");

    res.statusCode = 200;
    res.setHeader("Content-Type", "application/json");
    res.end(JSON.stringify({ ok: true, method: req.method, url: req.url }));
  });
});

server.listen(8080, () => {
  console.log("Server: http://127.0.0.1:8080");
});
```

2. Запусти сервер:

```bash
node server.js
```

3. Создай `manual-http-client.js` (TCP-клиент для ручного ввода HTTP):

```js
const net = require("net");
const readline = require("readline");

const socket = net.createConnection({ host: "127.0.0.1", port: 8080 }, () => {
  console.log("Connected to 127.0.0.1:8080");
  console.log("Type HTTP lines manually");
  console.log("/end -> send empty line");
  console.log("/quit -> close client");
});

socket.on("data", (data) => process.stdout.write(data.toString()));
socket.on("end", () => console.log("\nConnection closed by server"));
socket.on("error", (err) => console.error("Socket error:", err.message));

const rl = readline.createInterface({
  input: process.stdin,
  output: process.stdout,
  terminal: true,
});

rl.on("line", (line) => {
  if (line === "/quit") {
    socket.end();
    rl.close();
    return;
  }
  if (line === "/end") {
    socket.write("\r\n");
    return;
  }
  socket.write(line + "\r\n");
});
```

4. Запусти клиент во втором терминале:

```bash
node manual-http-client.js
```

5. Введи `GET` руками (каждая строка + Enter):

```http

Host: 127.0.0.1:8080
Connection: close
/end
```

6. Введи `POST` руками (проверь `Content-Length`):

```http

Content-Length: 13

/end
{"x":"test"}
```

7. Сравни, что отправил клиент, с тем, что сервер вывел в `req.headers` и `body`.

### 2.2 Async Node.js и Event Loop

> Это **самая частая** тема на собеседовании Node.js junior.

#### Теория

**Event Loop** — механизм, который позволяет Node.js обрабатывать тысячи одновременных соединений в одном потоке. Порядок фаз:

```
timers          ← setTimeout, setInterval
pending I/O     ← системные колбэки
idle, prepare   ← внутреннее
poll            ← I/O-колбэки (файлы, сеть, БД)
check           ← setImmediate
close           ← socket.on('close')

Между каждой фазой: microtask queue (Promise.then, queueMicrotask)
                  + process.nextTick (ещё до microtask)
```

**Эволюция асинхронности:**
- Callbacks → Promises → async/await
- `Promise.all()` — параллельно ждать все (падает при первом reject)
- `Promise.allSettled()` — параллельно, но собрать все результаты (успех+ошибки)
- `Promise.race()` — первый результат (используется для тайм-аутов)

**Блокировка event loop:** тяжёлая синхронная операция (JSON.parse огромного файла, crypto, цикл) замораживает весь сервер.

**EventEmitter** — базовый паттерн Node.js. Модули `http`, `net`, `fs`, `stream` наследуют от `EventEmitter`. Позволяет подписываться на события и публиковать их:

```js
const { EventEmitter } = require("events");
const emitter = new EventEmitter();
emitter.on("order:created", (order) => console.log("new order", order.id));
emitter.emit("order:created", { id: 42 });
```

**Streams** — абстракция для работы с данными чанками, без загрузки всего в память:
- `Readable` — источник (файл, HTTP-запрос, результат запроса к БД)
- `Writable` — приёмник (файл, HTTP-ответ)
- `Transform` — преобразование (gzip, CSV-парсер)
- `.pipe()` — соединяет потоки: `fs.createReadStream(file).pipe(gzip).pipe(res)`

Без Streams: весь файл читается в RAM за раз. Со Streams: данные идут чанками, память не растёт линейно с размером файла.

## 6. Краткие ответы

### A1 HTTP-статусы
- `200 OK`: успешный запрос с телом ответа.
- `201 Created`: создан новый ресурс.
- `204 No Content`: успех без тела ответа.
- `400 Bad Request`: некорректный запрос.
- `404 Not Found`: ресурс не найден.
- `409 Conflict`: конфликт состояния (например, дубликат).
- `422 Unprocessable Entity`: валидация не прошла.
- `500 Internal Server Error`: ошибка сервера.

### A2 Edge-cases
- Edge-cases выявляют баги на границах входных данных: пустые значения, `null`, длинные строки, переполнение, дубликаты.
- Без edge-case тестов система кажется рабочей, но падает в проде на редких сценариях.

### A3 Индексы

**Типы индексов в PostgreSQL:**
- **B-tree** (по умолчанию) — для `=`, `<`, `>`, `BETWEEN`, `LIKE 'abc%'`. Подходит для большинства случаев.
- **Hash** — только для `=`, не поддерживает диапазоны и сортировку.
- **GIN** — для массивов, JSONB, полнотекстового поиска.

**Составной индекс** `(a, b)` — используется запросами `WHERE a=?` и `WHERE a=? AND b=?`, но **не** `WHERE b=?` одним. Порядок колонок важен.

**Partial index** — индекс только по части строк: `CREATE INDEX ON orders(user_id) WHERE status='active'`. Меньше размер, быстрее обновление.

**Covering index** — покрывает все колонки запроса → index-only scan, таблица не читается.

Когда индекс **вреден**: малая селективность (булевый флаг), маленькая таблица, частые INSERT/UPDATE/DELETE.

`EXPLAIN ANALYZE` — смотри `Index Scan` vs `Seq Scan` и `actual time`.

### A4 ACID

| Свойство | Смысл |
|----------|-------|
| **Atomicity** | Транзакция выполняется целиком или откатывается полностью |
| **Consistency** | После транзакции все constraints выполнены, БД в допустимом состоянии |
| **Isolation** | Параллельные транзакции не видят промежуточных состояний друг друга |
| **Durability** | После COMMIT данные сохранены даже при сбое питания |

**Уровни изоляции** и допускаемые аномалии:

| Уровень | Dirty Read | Non-Repeatable Read | Phantom Read |
|---------|:---:|:---:|:---:|
| Read Uncommitted | ✓ | ✓ | ✓ |
| **Read Committed** (PG default) | ✗ | ✓ | ✓ |
| Repeatable Read | ✗ | ✗ | ✓ |
| Serializable | ✗ | ✗ | ✗ |

- **Dirty Read** — читаешь незакоммиченные изменения другой транзакции.
- **Non-Repeatable Read** — один `SELECT` возвращает разные значения в рамках транзакции (другая закоммитила изменение).
- **Phantom Read** — повторный `SELECT` видит новые строки (другая вставила и закоммитила).

### A5 Стратегии кэша
- Cache aside: приложение само читает/пишет кэш.
- Write-through: запись сразу в кэш и БД.
- TTL и инвалидация обязательны, иначе старые данные приводят к ошибкам.

### A6 Монолит vs микросервисы
- Монолит проще на старте: меньше операционной сложности.
- Микросервисы дают изоляцию и масштабирование, но повышают сложность инфраструктуры.
- Для Junior и первых проектов обычно достаточно модульного монолита.

### A7 Базовая безопасность

**SQL Injection** — никогда не конкатенируй ввод пользователя в строку запроса:
- Плохо: `` `SELECT * FROM users WHERE id = ${req.params.id}` ``
- Хорошо: `db.query("SELECT * FROM users WHERE id = $1", [req.params.id])`
- ORM защищают автоматически при правильном использовании.

**XSS (Cross-Site Scripting)** — вредоносный скрипт внедряется на страницу. Backend: `Content-Security-Policy` через `helmet`, не возвращать пользовательский HTML без санитизации. Хранение токенов в `HttpOnly` cookie — JS не сможет их украсть.

**CSRF** — сторонний сайт отправляет запрос от имени авторизованного пользователя. Защита: `SameSite=Lax/Strict` на cookie, CSRF-токен для форм. JWT в `Authorization` заголовке не страдает — браузер его не добавляет автоматически.

**Broken Access Control** (OWASP #1) — проверяй права на каждом endpoint, не только на UI. Пользователь A не должен получать/менять данные пользователя B.

**Rate limiting** — `express-rate-limit` или Redis-based лимитер. Защита от brute force и DDoS.

**Хранение паролей** — `bcrypt` (cost ≥ 12) или `argon2id`. Никогда: MD5, SHA1, plain text, обратимое шифрование.

### A8 Покрытие тестами
- Высокое покрытие не проверяет качество самих проверок.
- Можно иметь 100% coverage и не тестировать важные бизнес-сценарии.
- Нужны осмысленные тест-кейсы, включая негативные и интеграционные.

### A9 Secrets и env
- Никогда не коммитить API ключи, пароли, private keys.
- Использовать `.env` локально и секрет-хранилища в CI/CD и облаке.
- Добавить пример `.env.example` без секретов.

### A10 Диагностика latency
- Проверить: БД-запросы, индексы, сетевые вызовы, блокирующие операции.
- Сравнить p50/p95/p99 latency.
- Добавить трассировку запроса по слоям (API -> service -> DB/external).

### A11 Как отвечать на собесе
- Если не знаешь: проговорить гипотезу, уточнить вводные, предложить проверку.
- Важна структура: проблема -> варианты -> компромисс -> выбор.
- Не угадывать уверенно, лучше показать инженерное мышление.

### A12 Пагинация
- **Offset** (`OFFSET 20 LIMIT 20`): просто, но медленно на больших offset и нестабильно при вставках.
- **Cursor** (`WHERE id > 42 LIMIT 20`): быстро и стабильно, но нельзя перепрыгнуть на произвольную страницу.

### A13 Event Loop
- Node.js — однопоточный с неблокирующим I/O.
- Фазы: timers → pending I/O → poll → check → close.
- Между фазами: `process.nextTick()` → microtask (`Promise.then`) → следующая фаза.
- Порядок: `nextTick` → `Promise.then` → `setTimeout(0)` → `setImmediate`.

### A14 Где хранить JWT

| | `localStorage` | `httpOnly cookie` |
|--|:---:|:---:|
| **XSS-уязвимость** | Да — JS читает токен | Нет — JS не имеет доступа |
| **CSRF-уязвимость** | Нет | Да — нужен `SameSite=Lax/Strict` |
| **Удобство реализации** | Просто — `Authorization: Bearer` | Сложнее — управление cookie |
| **Мобильные / SPA** | Удобно | Сложнее |

**Рекомендация для веб-приложений:** `httpOnly; Secure; SameSite=Lax` cookie + refresh token. `SameSite=Lax` закрывает большинство CSRF-атак без CSRF-токена.
